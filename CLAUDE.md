## Commands

### Backend (`backend/`, NestJS + Prisma v7)
```bash
npm run start:dev        # http://localhost:3000, watch mode
npm run build             # nest build
npm run lint               # eslint --fix
npm test                   # jest, unit specs (*.spec.ts)
npm test -- custodias.service   # run specs matching a name pattern
npm run test:cov
npm run test:e2e           # jest --config ./test/jest-e2e.json (backend/test/app.e2e-spec.ts)
npx prisma migrate dev --name <nombre>   # new migration, uses prisma.config.js for the DB URL (not schema.prisma)
npx prisma generate
node prisma/seed.js        # full sample data across every module (heavy)
node prisma/seed.minimal.js # minimal data: 1 company, 2 users, 1 project/tasks, basic Personal module (npm run seed:minimal)
```
Prisma v7 note: `schema.prisma` has no `datasource url` — the connection URL lives in `backend/prisma.config.js` (reads `DATABASE_URL` from env). Don't add `url` back to the datasource block.

### Frontend (`frontend/`, React 18 + Vite)
```bash
npm run dev        # http://localhost:5173
npm run build       # tsc -b && vite build
npm run lint
```
Since 2026-10-15 the frontend has **vitest** (`npm test`, `vitest.config.ts`), used only for pure logic (the Cotizador in `src/utils/cotizador/*.test.ts` and the Ecuador-day helpers of the Bitácora in `src/utils/bitacoraFechas.test.ts`); there are no component/page tests, so don't assume other code is covered.

### Browser extension (`extension-bitacora/`, 2026-10-29)
No build step: `src/` is the extension itself (load it unpacked only for testing). `node build.mjs --dev http://localhost:3100/api` writes a `dist/` copy pointing at the local server (and its `localhost` permission), `node build.mjs` one for production; `npm test` (inside that folder) runs `node --test` on the pure logic in `src/lib.js`. The server rules (`backend/src/modules/bitacora/bitacora-extension.util.ts`) and `lib.js` (domain, schedule) must be kept in step.

### Local infra
Dev uses a **local Postgres + Redis**, fully separate from the production Cloud SQL instance — create/edit/delete during local testing never touches real data:
```bash
docker compose up -d db redis      # Postgres 16 (port 5432) + Redis (port 6379), from the base docker-compose.yml
cd backend
npx prisma db push                 # builds the full current schema (migrations folder is stale/incomplete — don't use `migrate deploy`)
npm run seed:minimal               # minimal test data: 1 company, 2 users, 1 project/tasks, basic Personal module data
```
`docker-compose.dev.yml` is an override file only (bind-mounts `backend/`, forces `NODE_ENV=development`) — it defines no `db`/`redis` of its own; only combine it with the base file if you also want to run the `backend` service inside Docker (`docker-compose -f docker-compose.yml -f docker-compose.dev.yml up`), which isn't the normal flow (normal flow is `npm run start:dev` outside Docker, pointed at the local `db`/`redis` containers).

Only fall back to the Cloud SQL Auth Proxy (`scripts/start-db.ps1`'s previous approach, see `AGENTS.md`) for read-only inspection of real production data — never as the default local `DATABASE_URL`.

`prisma db push` against the local DB warns that it will drop tables the server creates at startup (e.g. `AuthAttempt`, because they are not in `schema.prisma`): **don't accept that warning** (`--accept-data-loss`); start the server instead and the new tables are created at startup, as in production.

### Backend unit test pattern
Services take a single `PrismaService` dependency, so specs instantiate the class directly (`new XService(mockPrisma as unknown as PrismaService)`) instead of spinning up a Nest `TestingModule` — faster and enough for pure unit coverage. `mockPrisma` is a plain object of `jest.fn()`s shaped like the Prisma delegates the service actually calls (e.g. `{ custodia: { findFirst: jest.fn(), ... } }`), not a real `PrismaClient`. See `custodias.service.spec.ts`, `permissions.service.spec.ts`, and `ventas-contratos.service.spec.ts` for the pattern, including how `ventas-contratos.service.spec.ts` handles `jest.mock('fs')`/`jest.mock('axios')` (spying on the real built-in `fs` module directly causes a "Cannot redefine property" error in this project's Jest/Node combo — always auto-mock it instead). `eslint.config.mjs` has a `**/*.spec.ts` override that downgrades `no-unsafe-*`/`unbound-method` to warnings, since Jest's own types (`expect.objectContaining`, `mock.calls`) are inherently `any`-typed.

## Architecture

### Deployment: everything through `cloudbuild.yaml`, triggered on push to `main`
A single Cloud Build trigger on `main` runs `cloudbuild.yaml` end to end:
1. Builds `backend/Dockerfile` (NestJS API only, no frontend) and deploys it to Cloud Run (`mejora-gemeseg-backend`, us-central1) with `--set-env-vars=NODE_ENV=production,REDIS_HOST=,REDIS_PORT=6379,GOOGLE_VERTEX_PROJECT=agentes-504115,GOOGLE_VERTEX_LOCATION=us-central1,GOOGLE_VERTEX_MODEL=gemini-2.5-flash`, `--min-instances=0` (cold start after idle; avoids a permanent Prisma pool against `db-f1-micro`) and `--set-secrets` for `DATABASE_URL`, `JWT_SECRET`, `FRONTEND_URL`, `SIGNWELL_API_KEY`, `GOOGLE_SERVICE_ACCOUNT_JSON`. Prisma's `pg` pool is capped at 3 (`DATABASE_POOL_MAX`, default in `prisma.service.ts`) so 10 Cloud Run instances cannot open 100 DB connections. `REDIS_HOST` is deliberately left empty, so `CacheService` (`cache.service.ts`) takes its "not configured" branch and disables caching entirely in production (every `get()` is a no-op returning `null`) — locally, `docker-compose.yml`'s `redis` service gives dev a real cache, so cache-related behavior can differ between the two environments; don't assume a cache-hit path verified locally also happens in prod. The last secret, `GOOGLE_SERVICE_ACCOUNT_JSON`, is the full content of `backend/google-service-account.json` (gitignored, never baked into the Docker image) — `DriveService`/`GmailMailService` fall back to this env var when the file isn't present on disk (see `getDriveClient()` in `drive.service.ts`). Without it, every Drive-backed RRHH feature (Reclutamiento sync, Cumplimiento, Guardias) fails in production with "Google Drive no configurado" even though it works locally — this exact regression shipped on 2026-09-04 (commit `f52e7f0` dropped the old `GOOGLE_SERVICE_ACCOUNT_JSON` env-var fallback) and was fixed 2026-09-11.
2. Builds the frontend (`npm ci && npm run build` in `frontend/`, `VITE_API_URL` set inline in the build step) and deploys it to **Firebase Hosting** using Google's official Firebase CLI builder image for Cloud Build (`us-docker.pkg.dev/firebase-cli/us/firebase`, per [Google's own docs](https://cloud.google.com/build/docs/deploying-builds/deploy-firebase)) — not `npx firebase-tools` on a generic `node:20` image. This builder correctly uses Cloud Build's *ambient* service-account identity (`141953681725@cloudbuild.gserviceaccount.com`), which already has `roles/firebasehosting.admin` + `roles/firebase.admin` (the latter includes the "API Keys Viewer" permission the official docs call out as required) — **no key file, no secret, no `GOOGLE_APPLICATION_CREDENTIALS` needed for this step.**
   Two things that did **not** work here, so don't reintroduce them: (a) `npx --yes firebase-tools deploy` on generic `node:20` relying on the same ambient identity — it doesn't reliably pick it up (got a 401 with no credentials found, even with the right IAM roles granted); (b) a `firebase login:ci` personal-account token (`FIREBASE_TOKEN`) — it worked when tested locally (misleadingly — the local machine had its own cached `firebase`/`gcloud` login as a silent fallback) but failed inside Cloud Build's isolated container with a 400 on the OAuth refresh call (a dead/revoked refresh token), surfaced only as a useless generic `Assertion failed: resolving hosting target...` unless you add `--debug`. A downloadable service-account key was also considered and rejected: this GCP org has `iam.serviceAccountKeys.create` blocked by policy, so `gcloud iam service-accounts keys create` fails with `PERMISSION_DENIED` even for the project owner.

`firebase.json` proxies `/api/**`, `/health`, `/docs/**` from Hosting to the Cloud Run service, so the two deploy from the same build but are served under one origin. The production URL is a custom domain (`app.gemeseg.com`) mapped onto Firebase Hosting, not the raw Cloud Run URL. Don't reintroduce building the frontend into `backend/Dockerfile` — keep it as a separate step in `cloudbuild.yaml` so a frontend-only failure doesn't block the backend deploy (they're sequential steps in the same build, not merged into one).

A GitHub Actions workflow (`.github/workflows/firebase-hosting-merge.yml`) once tried to deploy the frontend this same way, but was removed (2026-09-11): it needed a `FIREBASE_SERVICE_ACCOUNT` repo secret that was never configured, so every run failed at the deploy step, and it duplicated what Cloud Build now does anyway. Don't re-add a GitHub Actions deploy path without first checking whether it's actually needed alongside the Cloud Build one above.

### Scheduled jobs are HTTP endpoints hit by Cloud Scheduler, never `@Cron`
`ScheduleModule` is registered but nothing uses `@Cron`: with `--min-instances=0` an instance may be asleep, and Redis/BullMQ is off in production. Daily jobs (Contratación Pública `entregas-cron/recordatorios`, task due-date reminders `POST /tasks/reminders-cron/run`) are public endpoints protected by the `x-cron-secret` header = `CRON_SECRET` (no variable → 404, wrong header → 401, `?dryRun=true` lists without sending). Since 2026-10-14 the `CRON_SECRET` secret exists in Secret Manager, is listed in `--set-secrets` of `cloudbuild.yaml`, and the Cloud Scheduler job `tareas-recordatorios-diarios` calls the task-reminders endpoint daily at 9:00 Guayaquil; the Contratación Pública job still has to be created. Ventas has a third public daily endpoint of the same kind, `POST /ventas/renovaciones-cron/generar` (opens the renewal opportunity of every service contract ending in 30 days or less; its Cloud Scheduler job `ventas-renovaciones-diarias` was created 2026-10-22, daily 6:00 Guayaquil, see `.agents/modules/ventas-contratos.md` section 24). **Order matters for any new secret: create it in Secret Manager before adding it to `--set-secrets`, or the whole backend deploy fails.** Never print the output of `gcloud scheduler jobs create/update` — it echoes the `x-cron-secret` header in clear. The local `gcloud` defaults to another project (`capacitaciongemeseg`): always pass `--project=mejora-gemeseg` (details in `AGENTS.md`, Tasks, and `.agents/modules/contratacion-publica.md`). The Bitácora has a fourth public endpoint of the same kind, `POST /bitacora/google-cron/sincronizar` (reads the Google activity of the activated people; hourly; its Cloud Scheduler job `bitacora-google-cada-hora` was created 2026-10-27 (every hour at :30, Guayaquil); `GOOGLE_WORKSPACE_ADMIN_EMAIL` is already in `cloudbuild.yaml` and the mail service account + `CRON_SECRET` already exist as secrets, see `AGENTS.md`, «Bitácora del equipo»).

### Files that must survive a restart go through `StoredFile`, never straight to disk
Cloud Run's disk is wiped whenever an instance is recycled (`--min-instances=0`). Anything the app generates or receives and must keep (Ventas and Contratación Pública `.docx` templates, Ventas contract PDFs — generated and signed) is saved with `common/utils/stored-file.util.ts`: the real content goes to the `StoredFile` table (unique logical key, e.g. `ventas/contracts/<file>.pdf`) and the disk is only a cache (read: disk → database, rewriting the disk). `ventas/ventas-files.util.ts` groups the Ventas paths and keys. **Any new file that has to outlive a restart must use these helpers, not `fs.writeFileSync` directly.** Still affected: Contratación Pública monthly-report PDFs (regenerable). Company logos use the same table (key `companies/logos/...`, served publicly by `CompanyLogosController`; see `AGENTS.md`, "Empresas").

### A new column on an EXISTING table must be created at startup, before any query (2026-10-15)
Deploys don't run migrations, and Prisma selects every column of a model on every query without a `select`, so declaring a column in `schema.prisma` that production doesn't have yet breaks every query on that table (for `User`, every login). New *tables* are created at startup by their own schema services (`VentasSchemaService`, `UserPreference`...), which is harmless because only new code reads them. A new *column* on a table that already exists (first case: `User.phone`, `src/prisma/user-phone.schema.ts`) is added with `ADD COLUMN IF NOT EXISTS` inside `PrismaService.onModuleInit`, right after connecting, and the server must fail to start if it fails. Keep it additive and nullable so the previous deploy keeps working (safe rollback), and keep the matching `prisma/migrations/<date>_*/migration.sql` as reference only.

### Expired sessions in the frontend
The JWT lasts 7 days. `auth.service.ts` checks the token's `exp` in `isAuthenticated()`, and a response interceptor logs out on any 401 outside `/auth/` and sends the user to `/login` with "Tu sesión expiró". Before 2026-09-30 an expired token left the app open with every call failing silently and the menu collapsed to Inicio/Buzón/Encuestas/Proyectos (Ctrl+F5 did not fix it because the token stays in `localStorage`). `usePermissions` retries (1 s, 3 s) when loading permissions fails, keeps the last good load instead of emptying the menu, and shows "No se pudieron cargar todos tus módulos" with a retry button if it never loaded.

### Authorization has two independent layers — check both when adding a route
1. **Role guard** (`common/guards/roles.guard.ts` + `@Roles(UserRole.ADMIN)` decorator): coarse ADMIN/MANAGER/EMPLOYEE check, enforced per-endpoint.
2. **Section permissions** (`modules/permissions/`): a separate, DB-backed system gating whole feature areas. `PermissionsService.ALL_SECTIONS` is the master list (DASHBOARD, PROJECTS, ADMIN, CACAO, COMPANY_SETTINGS, COMPANIES, CUSTODIAS, RRHH, VENTAS, CONTRATACION_PUBLICA, SISTEMAS, BITACORA). A company only sees a section if it's `alwaysEnabled` or explicitly turned on via `CompanySection` (set through `/admin/permissions`, super-admin only); within an enabled section, individual users can be further restricted per-section via `UserPermission.canView/canWrite` (set through `/admin/user-permissions`, company-admin). Super admin (`companyId: null`) bypasses all of this and sees every section. "No `UserPermission` row" means *allowed*, except in the closed-by-default sections (`SECCIONES_CERRADAS_POR_DEFECTO`, today `SISTEMAS` and `BITACORA` — Herramientas is a Sistemas screen, not its own section; `BITACORA` is also `alwaysEnabled: false`, so a super admin must turn it on per company): there it means *no access* (2026-10-14). Also since 2026-10-14: `User.password` is omitted from every Prisma query (`PrismaService` global `omit`; only `auth.service.ts` asks for it), there is no public registration, and login / password-reset requests / change-password are rate-limited through the `AuthAttempt` table (details in `AGENTS.md`, Auth, and `.agents/modules/users.md` section 7).

   On the frontend, `contexts/PermissionsContext.tsx` + `hooks/usePermissions.ts` expose `canView(section)`, consumed by the `<SectionRoute section="...">` wrapper in `App.tsx` around every module's routes. Adding a new module means: add it to `ALL_SECTIONS`, gate its API endpoints, and wrap its frontend routes in `SectionRoute`.

   Two more rules that live across several files (2026-10-06): (1) the **Gerente (MANAGER)** sees Administración, Mi Empresa and Permisos usuarios read-only *by role* (`SECCIONES_VISTA_GERENTE` in `usePermissions.ts`, ignoring the per-user checkboxes); only the GET endpoints accept `@Roles(ADMIN, MANAGER)`, everything that writes stays ADMIN-only, and in the UI the blocked buttons stay visible and open `SoloAdminDialog` («solo para administradores, contacta a uno de tu empresa») instead of hiding. (2) **Changing/resetting a password closes the user's other sessions** through the `UserSessionCutoff` table (`auth/session-cutoff.service.ts`; `JwtStrategy` rejects tokens whose `iat` is older, fails open, 30 s in-memory cache); the table is created at startup like `UserPreference` because deploys don't run migrations. Herramientas is no longer a section (`TOOLS` left `ALL_SECTIONS`): it is governed by `SISTEMAS`.

   This permission model is not documented in `AGENTS.md` yet — update that file's "Reglas de Negocio" section if you change it.

### Multi-tenancy via `companyId`, not a shared-nothing model
`User.companyId` is the only tenancy boundary; most other domain data (projects, tasks, cacao, custodias, ventas records) is scoped indirectly through the acting user, not through its own `companyId` filter everywhere — check each service's query before assuming isolation is automatic. `companyId: null` on a user means super-admin (see `admin@general.com`), not "no company" — that sentinel shows up throughout `permissions`, `companies`, and `ventas` services (e.g. `SuperAdmin Handling` in `.agents/modules/ventas-contratos.md`).

### Domain modules under `backend/src/modules/`
Each is a self-contained NestJS module wired into `app.module.ts`. Business-facing ones beyond the core PM/admin stack (`auth`, `users`, `projects`, `tasks`, `tools`, `agents`, `companies`, `ai`, `queue`, `cache`, `permissions`):
- **`cacao/`** — cacao trading back-office, split into its own sub-modules (`suppliers`, `clients`, `receptions`, `lots`, `settlements`, `shipments`, `payables`, `receivables`, `price-fixings`, `qualities`, `kardex`, `unit-config`, `dashboard`). Each is CRUD-ish and mirrors a physical business process (reception → lot → settlement → shipment → payable/receivable). Since 2026-10-23 a settlement is born `PENDING` and only creates its payable when a manager/admin other than its creator approves it; the server recomputes every settlement total, caps each lot at what that supplier delivered minus what is already settled (not `CacaoLot.netWeight`, which shipments lower), and payments/receipts are validated, run in a locked transaction and can be voided (see `.agents/modules/cacao.md`, «Liquidaciones, aprobacion y pagos»). Cacao is **white-label (línea blanca, 2026-10-23)**: qualities, lot codes, the sack weight (`CacaoUnitConfig`) and the payment/collection terms (`CacaoSetting`) are per company, a new company starts empty (the Dashboard shows a «Primeros pasos» checklist) and nothing is hardcoded to Mikacao; in the menu it is a dropdown with the Dashboard first. Receptions and shipments run in one locked transaction and the server recomputes shipment cost/amount/margin (sale price is $/kg). Its new columns and tables live in `src/prisma/cacao-liquidaciones.schema.ts` and `src/prisma/cacao-config.schema.ts` (startup DDL, same rule as the next section; the latter also swaps two global unique indexes for per-company ones).
- **`custodias/`** — route/transport/payroll module for security escort trips. Naming: "Custodias" = trips/payroll here; the security *staff* live in `personal` under "Guardias". States flow `LISTO_PARA_CUSTODIAR → EN_CAMINO → LLEGO`, and payroll only settles on `LLEGO`. Includes a "GEME-BOT" query assistant endpoint and PDFKit-generated PDFs (orden de custodia, nómina).
- **`contratacion-publica/`** — entidades públicas, entregas de documentos, y desde 2026-10-18 las Operaciones y las **Bitácoras de guardianía**: foto de la hoja → el agente revisor (`agents/`, `scope BITACORAS`, no conversa) la **transcribe sin conocer el horario** → código fijo la compara con el horario del puesto y genera hallazgos. Tablas creadas al arrancar (como `StoredFile`, la foto no va a Drive); lo que hace cada agente trabajador se documenta en `agent-trabajadores.const.ts` y su actividad queda en `AgentRun`, visible en Sistemas → Agentes. Ver `.agents/modules/contratacion-publica.md` y `agents-ai.md` punto 5.
- **`personal/`** — HR: recruitment pipeline (Google Drive sync for candidate docs — no Kanban board, that was removed 2026-09-17 as unused), trainings with expiry alerts, compliance checklists per employee (cédula), job positions, complaints, and surveys (which since 2026-09-22 can also be answered through an unauthenticated public link — `PublicSurveyController`, `/public/surveys/:token`, the only guard-less surface in the module). Certifications were removed entirely on 2026-09-22, table included. Every person's Drive folder is named `Apellidos Nombres` — no dash, no cédula, no puesto (`utils/nombre-persona.util.ts`); old formats are still parsed and only reported, never renamed.
- **`ventas/`** — sales/CRM: a **Posibles clientes** inbox (screen name since 2026-10-16, formerly «Leads» — Google Ads still calls them leads; `SalesLead`, API `/ventas/entrantes`, URL `/ventas/leads`; webhooks for the web form and Google Ads), **Directorio** (formerly «Clientes»: data-only list of every company/person, opens with everyone and no filters (a computed «Relación» column/filter); responsible, stage and follow-up belong to the opportunity; «Inactivo» = formerly «Ex-cliente», internal value `EX_CLIENTE`; URL `/ventas/clientes`; screen names and vocabulary rules in `.agents/modules/ventas-contratos.md` section 17), **Opportunities** (`SalesOpportunity`: each negotiation of a service, its own funnel/quote amount/loss reason; `SalesClient.status` is only a mirror of the main opportunity's stage), a computed client lifecycle, closing-reason catalog (`SalesReason`/`SalesReasonEntry`), the extended dashboard (`/ventas/analitica/*`), the separate **Agente de Ventas** (see `agents-ai.md` point 3; Agente Gemeseg no longer runs Ventas live queries); the **Cotizador** (menu "Cotizador", `/ventas/cotizador`; `Cot*` tables created at startup by `cotizador.schema.ts`; products are identified by code and "delete" only deactivates; see `.agents/modules/ventas-cotizador.md`); the old lead/visit/goal module is still in the backend but has no screen. **Ubicación opcional (2026-10-19, `ventas-contratos.md` section 26):** `SalesOpportunity.location*` (7 columnas nulas, creadas al arrancar) se elige en un mapa de OpenStreetMap/Leaflet con el buscador Nominatim pasando por el servidor (`ventas-ubicaciones.*`: 1 consulta/s, User-Agent propio, caché) y alimenta el mapa de Ecuador del Dashboard (`/ventas/analitica/mapa`; vistas burbujas, calor y puntos). Planificación y Campo (`ClientVisit`, visitas de campo; ENCENDIDA en el menú desde 2026-10-23) se conecta al Directorio y a las oportunidades: «Oferta y cierre» elige productos y servicios del catálogo, suma servicios y monto a la oportunidad abierta y propone su cambio de etapa (`ventas-contratos.md` sections 27 and 39). **Flow rule (2026-10-08, `.agents/modules/ventas-contratos.md` section 14):** lead → opportunity → client. The stage lives ONLY on the opportunity and is changed only in Oportunidades; since 2026-10-16 the Directorio (formerly Clientes) is data-only and lists everyone; a won opportunity or a valid contract makes the company/person a «Cliente» (computed «Relación»), `contratoPendiente` until a contract exists; the responsible and the next step belong to the opportunity. Stage keys (`RECIBIDO`..`RECHAZADO`) are hardcoded across analytics/AI, so only labels change (and `NEGOCIACION` was added); don't rename keys. Marketing phases (sin procesar / cualificado = «En evaluación» or later (since 2026-10-27, before it was quoted) / convertido = accepted) are computed from the opportunity, never stored (`ventas-marketing.util.ts`), mirroring Google Ads' funnel. Lead channels live in ONE registry (`lead-canales.const.ts`, served by `GET /ventas/entrantes/canales`; the source is mandatory on "Nuevo lead" and a new channel is one entry), and a lead that carries a `gclid` records `CUALIFICADO`/`CONVERTIDO` events (`SalesConversionEvent`) when its opportunity reaches En evaluación/is accepted (the hourly cron also back-fills missed ones), to be reported to Google Ads (the automatic send is built but OFF until the IDs are saved per company in Ventas → Configuración, table `SalesSetting`, which also holds the per-company landings table; `ventas-contratos.md` section 15). All the new tables are created at startup by `VentasSchemaService` (see `ventas-contratos.md` section 13), plus commercial contracts per client (`SalesAgreement`, menu "Contratos": services catalog, validity dates, renewals; API `/ventas/acuerdos`, tables created at startup by `sales-agreement.schema.ts`, see `ventas-contratos.md` section 12) and a document-generation subsystem (menu "Documentación", formerly "Contratos"; `SalesContract`, API `/ventas/contratos`, not renamed) (`ventas-templates.*`, `ventas-contratos.*`) that downloads a `.docx` from a Google Drive link, detects `[Variable]`/`<<Variable>>` placeholders (including table-type fields with configurable columns), fills them in and converts to PDF via headless LibreOffice, then sends it for e-signature through **SignWell** (`SIGNWELL_API_KEY`; BoldSign was fully removed 2026-09-17 — see below). See `.agents/modules/ventas-contratos.md` for the full design of that subsystem — it's the most detailed spec of any module in the repo and should be the first read before touching contracts/templates code.

- **`bitacora/`** — Bitácora del equipo (2026-10-27, deployed to production 2026-10-27 (PR #52); pilot only with the owner, nobody else is activated; since 2026-10-29 it also has a browser extension, see below): automatic daily record of what each person does, to check hours and work in virtual teams. It is its own sidebar module, **«Bitácora»**, with a submenu: Dashboard (`/bitacora`, team metrics over 7/14/30 days), Actividad del día (`/bitacora/actividad`, the full detail of one day), Mi hoja del día (`/bitacora/mi-hoja`) and Configuración (`/bitacora/configuracion`, tabs «Hojas del día» and «Google»), each shown only to who it applies to. **Opt-in per person, nobody by default**: company admins and managers turn each person on in Configuración → «Hojas del día» (`BitacoraActivacion`); nothing before the activation moment is recorded or read; turning off keeps the history and notifies the person. Two sources: a global `APP_INTERCEPTOR` (`ActividadInterceptor`) that notes every successful `POST/PUT/PATCH/DELETE` of an activated person (module, action, route, id and a short name taken from the response — never content; `GET`s don't count because the bell polls every 60 s) plus the login, and the Google Workspace Reports API (login and Drive, read person by person with the **mail** service account, not the Drive one). A third source, **the browser extension** (`extension-bitacora/`, Chrome and Edge, one Manifest V3 codebase with no dependencies; distributed **only through the stores**, never by manual or Workspace-forced install, because the product is meant to be sold to companies without Google), reports the **domain only** (never URL, title or content) and minutes, once a minute sampled and every 5 minutes sent, only inside the company schedule (Configuración → «Horario», `BitacoraHorario`; no schedule saved = nothing recorded), with the browser window in front and the person active, never in private windows. It links to the person's app.gemeseg account with a one-time code (10 min) from «Mi hoja del día» (`bitacora-extension.*`, token `bx_…` stored hashed, routes `/api/bitacora/ext/*` without a user session; CORS accepts `chrome-extension://` origins only on those routes) and **the server revalidates everything** (schedule, active sheet, valid domain, not future/old/before activation). Events are `fuente EXTENSION`, `modulo web`, with the new nullable `minutos` column created at startup. The day is an Ecuador day (UTC-5). Section `BITACORA` is closed by default and the controller requires an explicit `UserPermission` row even if the company marks it «fixed». Tables are created at startup (`bitacora.schema.ts`). Full rules, decisions and what's still pending (lawyer review and the notice to the team before activating anyone, switching the section on for the company) in `AGENTS.md`, «Bitácora del equipo».

Several `cacao/` and `personal/` and `ventas/` modules integrate with external services (Google Drive via `googleapis`, SignWell) — check for API keys/tokens in env/Secret Manager before assuming a feature works locally without them.

- A control that appears and disappears with content must NOT sit mid-row: render it always (disabled when it doesn't apply) or move it into `RowActionsMenu` (`components/common/RowActionsMenu.tsx`).
- **Every Ventas listing table has the «Exportar» arrow (2026-10-27): `<ExportTableButton>` (`components/common/ExportTableButton.tsx`), right after `ClearFiltersButton`.** It opens a modal to pick the columns, drag their order and choose Excel / PDF / CSV, and exports exactly the rows the table shows (filtered and sorted). Pass `columns` (all exportable, incl. the fixed first one), `defaultKeys` (what the person sees now), `rows` and `getValue(row, key)` returning PLAIN TEXT (cells render JSX). Optional `historial={(row) => ({ oportunidadId, clienteId, leadId })}` adds the «Historial» column (stage changes with their note, closing reasons, opportunity note, and the notes/calls/meetings/emails of the client's ficha), built by `VentasHistorialExportService` only when that column is chosen. - Clear-filters is always `ClearFiltersButton` (`components/common/ClearFiltersButton.tsx`): broom icon, no label, always rendered, disabled when there is nothing to clear. Don't hand-roll another one.
- **Modal overlays never close on a drag that started inside.** `utils/overlayClickGuard.ts` (installed once in `main.tsx`) drops an overlay `click` when the `mousedown` didn't start on that same overlay — selecting text in an input and releasing outside used to close ~70 modals. Keep using `onClick={onClose}` on `.modal-overlay`; don't re-implement the check per modal.
- **Ventas modals come in FOUR sizes only (2026-10-22): `modal modal-ventas-sm` (470px, confirmations), `modal-ventas-md` (740px, every form) and `modal-ventas-lg` (970px, editors with tables or maps).** Choose by CONTENT, not by habit: `sm` for confirmations, one-column lists and short forms (up to one row of two fields: stage change, stages and fields config, quick forms); `md` only when the form is long or has a service grid (opportunity, lead, contract, convert); `lg` for tables/maps; `xl` (1250px) ONLY for a full data manager whose whole table must be visible (the Cotizador catalog). A modal that is mostly empty space is the wrong size. Never write a width inline (`style={{ maxWidth }}` beats the class) and don't use `modal-lg`/`modal-xl` in Ventas. Other modules still use the old classes; migrate them to the same three sizes when touched.
- **Every listing table has the "Columnas" button (rule restated by the user 2026-10-08, no exceptions for new tables).** Ventas' Oportunidades, Posibles clientes, Contratos and Documentación got it that day; keep adding it to the older tables of other modules you touch.

Load every page of a paginated select, drop a saved value that is not among the options *before* querying, and store "no filter" as `''` read with `??` (not `||`). Filter bars made of input fields still get `ClearFiltersButton`; Inicio's pill-button bar deliberately has none (user's call, 2026-10-14).

- **Listing tables are «tablas vivas» automatically (2026-10-20, `utils/tablasVivas.ts`, section TABLAS VIVAS in `styles.css`).** Every `.tasks-table-wrapper` outside a modal scrolls inside its own height (what is left of the screen below where it starts), keeps the header fixed, shows the horizontal scrollbar always at its foot, can be dragged with the mouse, and pins its first column. Before this the scrollbar sat at the end of the whole list and was off-screen. Don't add `overflow`/`max-height` to these wrappers by hand. `data-fijas` on the `<table>` (0/1/2) sets how many leading columns are pinned (default 1). A screen with the «Columnas» menu gets the user-chosen pin for free: pass `pinned={columnPrefs.pinned}` + `maxPinned={columnPrefs.maxPinned}` to `ColumnPickerMenu`, `columnPrefs.set(keys, fijas)` in `onApply`, and `data-fijas={columnPrefs.fijas}` on the table (`useColumnPreferences` already returns `visible` with the pinned column first; the pin is stored under `columnas:<tabla>-fijas` because the server only accepts the `columnas:`/`notificaciones:` prefixes). Max 2 pinned in total = the main column + 1 chosen; a screen that already renders 2 fixed leading columns passes `{ columnasBase: 2 }` to the hook. Pinning only works if the screen renders columns in `visible` order (Bitácoras does not, so it has no pin choice). Below 768px nothing is pinned. `.page-container` is 1480px wide (was 1100px) so wide tables stop overflowing.
- **Listing tables get both resizing and sorting, by default.** Treat these as the baseline for any new listing table, not an extra:
  - `useResizableColumns('<key>')` (`hooks/useResizableColumns.ts`) + `className="tasks-table resizable-table"`. Drag the divider between two headers left or right; double-click the handle resets that column. Widths persist per viewer in `localStorage`. Note the hook returns a **callback ref**, not a `useRef` — with a plain ref the effect ran while the table was still behind a "Cargando..." branch and the handles never got installed.
  - **One button per column that sorts AND filters (2026-10-28, `RECOMENDACIONES_UX_UI.md` §25, `ventas-contratos.md` section 43):** `<th>Etiqueta <ColumnFilter cf={cf} col="campo" orden={…} /></th>` (`components/common/ColumnFilter.tsx` + `hooks/useColumnFilters.ts`). The panel has a one-line «Ordenar» (two directions; pressing the active one clears it) and the column filter below it; the button shows an arrow when sorted and an orange funnel when filtered. **Don't draw a loose `⇅` next to it.** Two ways to give the order: simple screens use `orden={cf.ordenDe('campo')}` (the filters hook sorts `cf.filas` with the value the column already declared for filtering — nothing to repeat); screens that already use `useSortableTable(rows, { campo: (r) => valor }, 'campoInicial')` (`hooks/useSortableTable.tsx`; header click, initial order, computed columns) use `orden={ordenDe('campo')}` from that hook and `<th {...thProps('campo')}>`. Never both in one table. Text compares with `localeCompare(…, 'es')` so accents and ñ land where they should; numbers as numbers; blanks always sort last. Every table with column filters has it (Ventas, Personal, Contratación Pública, Cacao, Custodias, Sistemas, Bitácora, Proyectos, Cotizador); dashboards and the contratación-pública bitácoras keep their sort-only `SortIcon`.
  - The two coexist: the resize handle swallows `mousedown` and `click` so dragging a width never reorders the table.
  - **Actions column → `col-acciones` on both `<th>` and `<td>`** (2026-10-02). `.resizable-table` is `table-layout: fixed`, so a column with no width gets an *equal share* of the table — an unsized "Acciones" column was ~200px wide for a 34px "⋯" button. `col-acciones` fixes it at 64px (header text goes in `<span className="visually-hidden">`, it doesn't fit visibly); add `col-acciones--ancha` (160px) only if the cell also holds one text button (e.g. "Hecho" in Clientes → Hoy). Several text buttons per row → move them into `RowActionsMenu` instead. Icon-only buttons visible in the row (no "⋯" menu), 32px each: up to three → `col-acciones col-acciones--ancha` (160px), up to four → `col-acciones col-acciones--iconos` (172px), always with a `<div className="acciones-iconos">` inside the cell. Give each button a fixed slot (render an empty `<span className="icon-btn">` when it does not apply) so icons line up from row to row. Used in Entidades Públicas, Contratos and the documents of each month (2026-10-05/06); in Contratación Pública no table uses `RowActionsMenu`. Inside `.header-actions` a lone icon button is `btn-icon-toolbar` (a `btn-secondary icon-btn` there gets squashed by the header padding). Text that navigates inside a table is `a.enlace-tabla` (no underline); never leave a bare `<a>` or a `<button>` without a class in these screens. Tables without `resizable-table` size automatically and don't need it. Guardias, Personal Administrativo and Encuestas (text buttons) don't use it yet.

### Frontend structure
- `src/pages/<module>/` mirrors the backend module split (`cacao/`, `custodias/`, `personal/`, `ventas/`, plus `admin/`, `projects/`, `tasks/`, `tools/`, `profile/`).
- `src/services/` are thin Axios wrappers (one per backend module), all going through a single JWT-interceptor Axios instance.
- Every non-trivial page is lazy-loaded (`React.lazy`) in `App.tsx`; new pages should follow that pattern rather than being imported eagerly.
- `contexts/ThemeContext.tsx` (`CompanyProvider`) drives white-label branding (colors/logo per company); `contexts/PermissionsContext.tsx` drives the section-gating described above.
