# Modulo: Contratacion Publica

## Descripcion
Gestion de contratos de seguridad privada con entidades del sector publico (SERCOP): entidades, contratos (con renovaciones, adendas y adjuntos), puestos de servicio, horarios mensuales de guardias con generador automatico de patrones de rotacion, e informes mensuales generados desde una plantilla `.docx`. Backend en `backend/src/modules/contratacion-publica/`, frontend en `frontend/src/pages/contratacion-publica/`.

## Submodulos backend
| Submodulo | Responsabilidad |
|---|---|
| `entidades/` | CRUD de entidades publicas (nombre, RUC, direccion) |
| `contratos/` | CRUD de contratos, renovacion (enlaza `contratoOrigenId`), adendas, adjuntos |
| `puestos/` | Puestos de servicio por contrato, guardias asignados (snapshot cedula+nombre, sin FK a RRHH), patron de rotacion |
| `codigos-turno/` | Catalogo de codigos de turno por empresa (D/N/L, libre) |
| `horarios/` | Horario por rango de fechas, celdas guardia x dia, generador de patron, cobertura minima, export PDF/Excel |
| `informes/` | Informe mensual: datos autogenerados + texto redactado + plantilla `.docx` -> PDF |
| `textos-institucionales/` | Catalogo clave -> texto reutilizable en informes |

## Puesto de Servicio
```prisma
model CPPuestoServicio {
  nombre, tipoTurno (8H|12H|24H), cantidadGuardias
  guardiasSimultaneosRequeridos Int @default(1) // minimo de guardias "trabajando" cada dia
  guardias CPPuestoGuardia[]       // snapshot cedula+nombre
  patronRotacion CPPatronRotacion? // patron guardado, uno por puesto
}
```
`guardiasSimultaneosRequeridos` es independiente de si el puesto usa o no el generador automatico — aplica tambien a horarios llenados 100% a mano (ver "Cobertura minima" abajo).

## Codigos de Turno
```prisma
model CPCodigoTurno {
  codigo, nombre, color, activo
  esDescanso Boolean @default(false) // true = no cuenta como "trabajando" para la cobertura minima
}
```
Sin este flag no hay forma de saber que codigos son de trabajo vs descanso — es explicito, no se infiere por nombre/codigo.

## Horario Mensual — rango de fechas libre (no mes calendario)
Un horario real casi nunca es del 1 al 30/31 (ej. "30 de julio al 29 de agosto"). Por eso:
```prisma
model CPHorarioMensual {
  fechaInicio DateTime
  fechaFin    DateTime
  anio Int // derivado de fechaInicio, solo etiqueta para el cruce con Informes
  mes  Int // derivado de fechaInicio, idem
  estado String @default("BORRADOR") // BORRADOR, ENVIADO, APROBADO, RECHAZADO
}
model CPHorarioCelda {
  horarioId, puestoId, cedula, nombreGuardia, fecha, codigoTurno
  @@unique([horarioId, puestoId, cedula, fecha])
}
```
- **Sin solapamiento**: al crear un horario se valida que su rango `[fechaInicio, fechaFin]` no se cruce con el de NINGUN otro horario existente del mismo contrato (sin importar su estado) — `CPHorariosService.create` -> `assertSinSolapamiento`.
- Flujo de estados: `BORRADOR -> ENVIADO -> APROBADO/RECHAZADO`, `RECHAZADO -> BORRADOR`. Solo se edita en BORRADOR.
- `CPHorarioCelda` es una fila por celda guardia x dia (no columnas fisicas), asi el reemplazo en lote de un puesto es `deleteMany` + `createMany` (`reemplazarCeldasPuesto`).

## Generador de Patron de Rotacion
Autocompleta el mes/rango en vez de llenar celda por celda. Algoritmo puro en `backend/src/modules/contratacion-publica/shared/patron-rotacion.util.ts` (`calcularPatronRotacion`) — misma funcion usada para el preview (no persiste) y para la generacion real, para que nunca diverjan.

**Modelo del patron** (uno por puesto, `CPPatronRotacion`):
```prisma
model CPPatronRotacion {
  puestoId Int @unique
  tramos Json               // [{codigoTurno, dias}, ...] ciclo ordenado
  coberturaSimultanea Int   // cuantos guardias trabajan a la vez en cada tramo
  ordenGuardias Json        // [{cedula, nombreGuardia}, ...] define el desfase
  fechaInicioCiclo DateTime
}
```

**Algoritmo**: `cicloLongitud = suma de dias de los tramos`. `numGrupos = guardias / coberturaSimultanea` (debe ser entero, si no se bloquea). `desfaseDias = cicloLongitud / numGrupos` (debe ser entero, si no se bloquea — evitar que un dia quede con cobertura despareja). Grupo `g` arranca desfasado `g * desfaseDias` dias respecto al inicio del ciclo.

**Ejemplo verificado — 3 guardias, cobertura 1, patron 2D-2N-2L** (ciclo=6, 3 grupos, desfase=2):
| Guardia | Día 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| G1 | D | D | N | N | L | L | D | D |
| G2 | L | L | D | D | N | N | L | L |
| G3 | N | N | L | L | D | D | N | N |
Cada columna (dia) tiene exactamente 1D+1N+1L.

**Mismo patron, 6 guardias, cobertura 2** (2 guardias simultaneos por turno, ej. puesto que necesita pareja): mismos `numGrupos=3`/`desfase=2`, pero cada grupo tiene 2 guardias con el mismo codigo ese dia — cada columna queda con 2D+2N+2L.

**Endpoints** (`backend/src/modules/contratacion-publica/puestos/patron-rotacion.service.ts` + `horarios.service.ts`):
| Metodo | Ruta | Descripcion |
|---|---|---|
| GET | `/contratacion-publica/puestos/:id/patron-rotacion` | Patron guardado del puesto, o `null` |
| PUT | `/contratacion-publica/puestos/:id/patron-rotacion` | Guarda/actualiza la configuracion (sin generar celdas) |
| POST | `/contratacion-publica/puestos/:id/patron-rotacion/preview` | Calcula sin persistir — usado por la mini-grilla del modal |
| POST | `/contratacion-publica/horarios/:id/generar-patron` | Calcula, guarda el patron (si `guardarComoPatronDelPuesto`, default true) y reemplaza las celdas del puesto en una transaccion |

Solo funciona con el horario en BORRADOR (`assertEditable`). Si el puesto ya tenia celdas cargadas ese periodo, el frontend pide confirmacion antes de llamar al endpoint (el backend no bloquea, solo sobreescribe — la decision de avisar es de UI).

## Cobertura minima de guardias simultaneos
Valida que, dia por dia, cada puesto tenga al menos `guardiasSimultaneosRequeridos` guardias con un codigo que NO este marcado `esDescanso`. **No se valida en cada edicion de celda ni en cada intercambio** (seria muy intrusivo) — se valida en un unico punto de control: `CPHorariosService.cambiarEstado` cuando la transicion es `BORRADOR -> ENVIADO`. Si hay incumplimientos, se bloquea la transicion completa y se devuelven **todos** los dias/puestos que fallan (no solo el primero), como un mensaje de error con una linea por incumplimiento (el frontend lo muestra con `white-space: pre-line`).

## Intercambio de turno
`POST /contratacion-publica/horarios/:id/intercambiar-turno` — intercambia el `codigoTurno` entre dos guardias del **mismo puesto** (el DTO exige `puestoId` explicito, para que nunca pueda cruzar celdas de puestos distintos) en una fecha puntual. Solo funciona en BORRADOR.

## Exportar PDF y Excel
`CPHorariosService.getPdfData` arma una estructura comun (`HorarioPdfData`: puestos -> guardias -> `porFecha`, mas `fechas` del rango real y `colorPorCodigo`), consumida por:
- `CPHorariosPdfService` (PDFKit, A4 apaisado) — `GET /horarios/:id/pdf`
- `CPHorariosExcelService` (ExcelJS, coloreando cada celda con el color del codigo de turno, igual que la UI) — `GET /horarios/:id/excel`

## Casos de uso de verificacion
### Validos
- 3 guardias/cobertura 1/patron 2D-2N-2L -> tabla exacta de arriba, envio (BORRADOR->ENVIADO) pasa.
- 6 guardias/cobertura 2/mismo patron -> cobertura doble por turno, envio pasa.
- Horario con rango 30 jul.-29 ago. (cruza mes calendario) se crea sin error.
- Puesto 24H con `guardiasSimultaneosRequeridos=2` llenado 100% a mano con 2 personas todos los dias -> envio pasa.
- Exportar el mismo horario a Excel y PDF -> mismo rango de fechas, codigos y colores.
- Abrir el generador para el mismo puesto en el periodo siguiente -> precarga el patron guardado.

### Invalidos (deben bloquear con mensaje especifico)
- Cobertura=2 con 5 guardias -> "La cantidad de guardias (5) debe ser multiplo de la cobertura simultanea (2)."
- Un tramo de 5 dias con 2 grupos de guardias (ciclo no divisible) -> error de desfase no entero (evita que un dia quede con cobertura despareja).
- Segundo horario del mismo contrato con rango que se solapa con uno existente -> rechazado, nombrando el horario en conflicto.
- Puesto 24H con `guardiasSimultaneosRequeridos=2` con un dia con solo 1 guardia trabajando -> bloquea el envio, listando el dia y puesto exactos.
- Generar patron, editar celdas o intercambiar turno sobre un horario que no esta en BORRADOR -> rechazado.
- Intercambiar turno con cedulas que no pertenecen al `puestoId` indicado -> rechazado.

Para el informe mensual a cada entidad hacen falta documentos que producen otras áreas (RRHH, Financiero, Operaciones, Legal). Antes se pedían y se esperaban sin saber qué faltaba ni de quién. **Decisiones del usuario** (no re-proponer lo contrario):
- Los documentos se asocian a la **entidad**, no al contrato (una entidad puede pedir varios documentos, no solo contratos).
- **Cada mes es una solicitud independiente** (`CPSolicitudMensual`, única por entidad+año+mes): lo que se pide, las fechas (una por documento) y las personas cambian cada mes y se editan siempre, también ya enviada. ## Carpeta única de Drive para todo Contratación Pública (2026-10-02)

**Decisiones del usuario** (no re-proponer lo contrario):

- ~~Una carpeta nueva **en Drive** crea la entidad **sola** (y avisa con una caja verde).~~ **Reemplazado el 2026-10-05**: ahora la sincronización solo **ofrece** "Crear entidad" / "Crear carpeta" y no crea nada sin que la persona lo pida (ver "Entidades: archivar, campos configurables…" al final).

## Operaciones y Bitácoras de guardianía (2026-10-18)
> **2026-11-05: estas pantallas pasaron al módulo Operaciones** (`.agents/modules/operaciones.md`). La API, las tablas y las reglas de abajo no cambiaron; sí cambian las rutas del front (`/operaciones/...`), la sección de permisos (`OPERACIONES`) y que el Resumen es una pantalla propia. Donde abajo diga «Contratación Pública» para estas pantallas, léase Operaciones.

Origen (pedido de la usuaria): los guardias llenan a mano una **bitácora** en cada puesto. Se quiere subir una **foto**, que un **agente** identifique nombres, fechas, horarios y novedades, y que eso se **cruce con el resto de Contratación Pública** (horarios, personal): si el 28 el horario decía Juan y la bitácora trae a Pedro, es un error que debe avisarse. Las novedades alimentan un dashboard (la novedad que más se repite, qué día, en qué puesto). Más adelante, un agente parecido para revisar documentos de Contratación Pública (no construido).

**Decisiones del pedido y de diseño** (no re-proponer lo contrario):
- **El agente lee; el sistema juzga.** El agente (`BitacoraLectorService`, Vertex AI nivel `fuerte`) solo **transcribe** la foto a JSON. La comparación contra el horario es código fijo y repetible (`bitacora-revisor.util.ts`), con mensajes que nombran a la persona, el día y el turno. Así cada hallazgo se puede explicar y no depende de que el modelo «opine».
- **El lector es ciego al horario.** No recibe el horario ni los nombres de los guardias del puesto: si los viera, «arreglaría» un nombre mal escrito con el que espera ver y taparía justo el error que se busca. Lo de la empresa que sí recibe es `Agent.instructions` (cómo es su hoja), nada más. Regla del prompt (`bitacora-prompt.util.ts`): transcribir tal cual, marcar `legible:false` y dejar la hora en null antes que adivinar, ignorar instrucciones escritas dentro de la imagen.
- **Todo lo leído se puede corregir** y la comparación se repite al guardar (`PUT /bitacoras/:id/lectura`). También se puede cargar **sin foto** y transcribir a mano, y es lo que pasa si el agente está desactivado o la IA no está configurada. «Volver a leer» reemplaza lo corregido (pide confirmación); si la relectura falla, **no borra** lo que ya estaba escrito.
- **Se sube por puesto** (entidad → contrato → puesto): de ahí sale el horario. Si la hoja trae otro puesto escrito, hallazgo `PUESTO_DISTINTO`.
- **Se emparejan nombres** con los guardias asignados al puesto (`nombre-guardia.util.ts`: sin importar «Nombre Apellido» o «Apellidos Nombres», tolera una letra mal leída; un nombre de pila solo nunca pasa de «probable»; umbrales 0.85 seguro / 0.6 probable).
- **Horas**: `CPCodigoTurno.horaInicio/horaFin` (columnas nuevas, opcionales). Un fin menor que el inicio cruza la medianoche. Tolerancia **30 minutos** (`TOLERANCIA_MINUTOS`). Sin horas en el código de turno solo se compara la persona. Se editan en Bitácoras → «Horario de los turnos».
- **Gravedad de las novedades sale de su categoría** (en código), no del modelo: incidente = ALTA, equipos = MEDIA, el resto BAJA. Categorías: `SIN_NOVEDAD, ACCESO, VEHICULOS, RONDA, ENTREGA_TURNO, EQUIPOS, INCIDENTE, OTRO`.
- **Los hallazgos** (`CPBitacoraHallazgo`): `GUARDIA_DISTINTO` (el horario decía A y trae a B; es UNO solo, no «ausente» + «de más»), `GUARDIA_AUSENTE`, `GUARDIA_NO_PROGRAMADO` (aparece estando libre), `GUARDIA_NO_ASIGNADO`, `HORARIO_DISTINTO`, `SIN_HORAS`, `NOMBRE_DUDOSO`, `NOMBRE_AMBIGUO`, `LECTURA_DUDOSA`, `NO_HORARIO`, `HORARIO_NO_APROBADO` (se compara igual, con aviso), `FECHA_FUERA_DE_CONTRATO`, `PUESTO_DISTINTO`, `FECHA_YA_CARGADA`. Resolver o descartar exige una **nota** y queda en el historial; al volver a revisar se conserva lo resuelto si el hallazgo es el mismo (misma `clave`). Resultado de la hoja: `CONFORME | A_REVISAR | CON_ERRORES | SIN_COMPARAR | SIN_REVISAR`.
- **Dashboard** (`GET /bitacoras/dashboard`): % de hojas que cuadran, hallazgos abiertos (y graves), novedad que más se repite, días con más novedades, por día de la semana, puestos con más novedades, hallazgos por tipo y las novedades graves. Por defecto, los últimos 90 días hasta hoy.
- **Permisos**: es parte de la sección `CONTRATACION_PUBLICA` (ver = mirar, escribir = subir, corregir, resolver, borrar). La empresa debe tener la sección habilitada (super admin) y la persona su permiso (admin de la empresa). No hay sección nueva.

## Agente Revisor de Entregas en «Por aprobar» (2026-11-09)
Cada documento que otra área entrega lo mira un agente y deja una nota para quien aprueba: **«Parece correcto»** o **«Revisar»** con el motivo. **Solo sugiere**: aprobar y rechazar siguen siendo de una persona.

**Decisiones de la usuaria** (no re-proponer lo contrario):
- Se revisa **solo al entregar** (no hay botón obligatorio). Qué mira: **firma o sello y vigencia** (más que se lea; si no se lee, es «Revisar»). **Periodo (2026-11-10):** también compara el **periodo que el propio documento dice cubrir** («del 24 de agosto al 23 de septiembre», «planilla de septiembre») con el mes de la solicitud; si no toca ese mes, «Revisar» con el rechazo propuesto. Un periodo que cruza de mes vale para los dos meses. Si el documento no dice qué periodo cubre, no se compara. El modelo no recibe el mes (solo lo lee); lo compara `evaluarEntrega` con `solicitud.anio/mes`. **Riesgo conocido:** un documento que legítimamente se pide de otro mes (p. ej. una planilla del mes anterior) saldrá como «Revisar»; es solo una sugerencia, pero si estorba hay que decidir una tolerancia por documento. **NO** comprueba que sea lo pedido (el nombre del documento).
- Si dice «Revisar», el cuadro del motivo del rechazo **ya viene escrito** con lo que vio el agente (solo si estaba vacío; se edita o se ignora). Nunca rechaza solo.

**Cómo está hecho** (`contratacion-publica/entregas/revision-ia/`):
- El modelo (Gemini, `modeloVertex('fuerte')`, ~1.000 a 3.000 tokens de entrada y ~100 de salida por documento) **describe**: `legible`, `tipoDocumento`, `seFirma` (un documento de ese tipo lleva firma o sello), `firmaOSello` (SI/NO/DUDOSO) y `fechaVencimiento` si el propio documento la escribe. El veredicto lo da **código fijo** (`evaluarEntrega`): «Revisar» si no se lee, si se firma y no se ve (o es dudoso) o si el vencimiento escrito ya pasó (día de Ecuador). Sin fecha de vencimiento no se puede saber si está vigente: se dice «no dice fecha de vencimiento».
- Archivos: PDF e imágenes directo; Word y Excel pasan antes por la misma conversión a PDF de la vista previa (`EntregasService.obtenerArchivo(id, actor, true, true)`, que además comprueba que el archivo cuelga de la carpeta del mes). Enlace externo, ZIP y más de 15 MB: estado `NO_LEIDO` con el motivo, sin llamar a la IA.
- Tabla nueva `CPEntregaRevisionIA` (una fila por documento, creada al arrancar por `EntregaRevisorService.onModuleInit`; `prisma/migrations/20261109_cp_entrega_revision_ia` es solo referencia; FK con borrado en cascada). Guarda `entregadoAt` de la entrega revisada: si el documento se entrega de nuevo, esa revisión deja de valer sola (no se toca `EntregasService.entregar`).
- **Quién la dispara:** el navegador de quien entrega, con una petición propia justo después de entregar (`EntregarModal` → `POST .../documentos/:id/revision-ia`, no frena la entrega). No es un trabajo en segundo plano porque en Cloud Run el servidor se puede apagar al responder. Si esa persona cierra la pestaña antes, el panel de revisión la pide solo al abrirse (una vez). Una revisión terminada no se repite (salvo error o «Volver a revisar» del personal de CP); una «revisando» de más de 3 minutos se da por perdida.
- Endpoints (`/contratacion-publica/entregas`): `POST documentos/:id/revision-ia` (`view`; solo el responsable del documento o el personal de CP; quien entrega no recibe el resultado, solo el estado), `GET documentos/:id/revision-ia` y `GET revision-ia?ids=1,2` (`write`).
- Frontend: `RevisionIA.tsx` (cuadro «Revisión del agente» en `RevisionPanel`, solo para quien revisa; sondea cada 4 s mientras dice «Revisando…»), etiqueta junto al nombre en `PorRevisarPage` (no se muestra «Sin revisar»).
- Agente `ENTREGAS` («Agente Revisor de Entregas», `SCOPES_SIN_CHAT`, sembrado por `AgentRunService`): se ve en Sistemas → Agentes con su documentación y su texto de «Instrucciones» (cómo son los documentos de la empresa); cada revisión queda en `AgentRun` (`REVISAR_ENTREGA`).

- **Periodo leído de la hoja:** el mes sale del nombre de la hoja («DICIEMBRE», «publicos-junio») y el rango de las columnas (`periodoDeHoja` en `horarios-importar.util.ts`: primer día de la primera columna + cantidad de columnas; el año es el que deja la fecha más cerca de hoy). FEBRERO (1…28, 1, 2, 3) da 1 feb – 3 mar. Si el nombre no trae el mes (PUBLICOS, PROGRAMADO) se piden las fechas. Si la primera columna no es el día 1 se propone también el día de corte.
- **Personas sin cédula (decidido por Leidy: basta el nombre):** si el nombre coincide con alguien de RRHH (`EmployeeDriveFolder`, sin importar el orden de apellidos) se asigna con su cédula real; si no, queda con un **identificador temporal** `SC-XXXXXXXXXX` (hash del nombre, igual para el mismo nombre) para que el puesto y los turnos coincidan, y se avisa que falta completar la cédula. Antes esas personas no se asignaban y el horario quedaba vacío. **No se crea la ficha en RRHH** (la ficha nace de las carpetas de Drive y necesita cédula). **Pendiente:** pantalla para reemplazar el identificador temporal por la cédula real.

- **Por entregar:** los botones «Ver detalle» y «Entregar» van apilados y la columna de acciones es más ancha (antes se cortaba el texto).
